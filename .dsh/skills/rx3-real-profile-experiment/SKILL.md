# Новый контролируемый опыт RX3 под профиль реального проекта

## Назначение

Используй этот навык, когда подтверждённая область переноса ЛИРА → RX3 не
покрывает профиль реального проекта и требуется новый контролируемый опыт.
Навык описывает подготовку, но **не** заменяет `docs/RX3_CONTROLLED_EXPERIMENTS.md`:
при расхождении приоритет всегда у того файла.

## Инварианты (нарушение = остановка)

1. Данные сечения (площадь, периметр, ПТМ, Ix, Wx, Iy, Wy, масса) **никогда не
   фабрикуются**: их создаёт RX3 по выбору инженера. Программа только
   проверяет запись по базе сортамента `rx3/rx3.rxdb`.
2. Ни один исходный файл не изменяется: базовая запись берётся **копией**,
   побайтовая идентичность и SHA-256 проверяются до и после.
3. Инженер создаёт базовый файл в RX3 сам и сохраняет его **Save As** в новый
   файл. Программа не запускает RX3 и не нажимает кнопки.
4. Опыт не разрешает расчёт и не открывает выпуск: `NOT_READY_FOR_ISSUE`,
   `rx38_force_generation_allowed = false`.
5. Марка стали, вид нагружения, вид опирания, коэффициент расчётной длины,
   температурный режим, требуемый предел огнестойкости и нагреваемые стороны —
   инженерные решения. Они записываются как заявленные, а не выведенные.

## Порядок

1. **Факты.** Определи по модели реального проекта: семейство (stiffness_type →
   `stiffnesses.json.raw_name`), число элементов, точные длины, поворот, наличие
   строк РСУ/усилий. Определи, есть ли профиль в `rx3/rx3.rxdb`
   (`ProfileRepository.search`) и есть ли уже запись этого профиля в корпусе
   `rx3/*.rx38` и `validation/*/template.rx38`.
2. **Заявка инженеру.** Назови точный профиль, сортамент, длину (токен из
   модели), вид нагружения и требуемый R, которые он должен задать в RX3, и
   попроси сохранить файл **Save As** в новое имя, не перезаписывая исходник.
3. **Приёмка базовой записи (read-only).**

   ```powershell
   python -m fireprotect.cli prepare-rx3-baseline-observation `
     --file <новый-файл.rx38> --mark <марка> `
     --standard "<сортамент>" --designation "<профиль>" `
     --length-m <длина> --stress-state "<вид нагружения>" `
     --required-r-min <R> --profile-db rx3/rx3.rxdb `
     --output-dir <новый-каталог>
   ```

   Команда замораживает копию, проверяет заявленную идентичность, тождества
   RX38 и совпадение с базой сортамента, и пишет `CHECKLIST.md`. Любое
   расхождение — отказ, а не подстановка.
4. **Наблюдение Phase A.** Инженер открывает **копию** в RX3, сверяет значения
   с `CHECKLIST.md`, расчёт не запускает, сообщает результат и скриншот.
5. **Регистрация области.** Только после подтверждённого наблюдения зафиксируй
   новый scope: SHA-256 и отпечаток записи, профиль, длина, вид нагружения, R,
   режим. Правка существующего подтверждённого scope запрещена.
6. **Phase B.** Отдельным шагом подготовь `generated.rx38`, меняя **только те
   поля, чья семантика уже подтверждена** для этого вида нагружения, и заявляя
   значения из конкретной перепроверенной строки источника. Остальные записи и
   поля — побайтово идентичны.
7. **Расчёт.** Выполняет инженер вручную: открыть → сверить → «Рассчитать» →
   «Сохранить в таблицу» → Save As в новый `calculated.rx38`.
8. **Сравнение.** Проектный diff со строгой целью (отпечаток или позиция
   BEFORE), проверка результатных полей 44/54, отсутствие изменений нецелевых
   записей, отделение нормализации токенов от изменения значения.
9. **Отчёт.** Наблюдение отдельно от интерпретации; отрицательный результат
   фиксируется так же явно, как положительный.

## Чего нельзя делать

- Подставлять ближайший профиль из корпуса («25К1 похож на 25Б2») — это
  фабрикация сечения и потеря происхождения.
- Объединять несколько профилей или длин в одну запись по совпадению марки.
- Объявлять перенос подтверждённым для профиля, длины, поворота или вида
  нагружения, которые не были предметом опыта.
- Считать открытие файла в RX3 или зелёные тесты доказательством корректности
  расчёта.
